## Verdict

**Ease of use.** The core authoring loop genuinely delivers the pitch: `dotnet new loom` is ~50 lines to a triangle, a full deferred+shadows+SSAO+bloom+picking frame is 193 lines of declarations, and reusable sub-graphs (the bloom pyramid) compose as plain extension methods with zero ordering/barrier code. The cliff is *immediately after* the triangle: the packaged `LoomApplication` host exposes **no input, no surface size, no engine settings, no exit** — every real game today must abandon it and copy the sandbox's 882-line hand-rolled host (L-01/L-02/L-03). Fixing the hosting layer is the single highest-leverage block of work in this review.

**Scale in a large game.** The derive-once story is real and the steady-state frame is *almost* allocation-free (three small leaks: L-20, L-21, L-47). Derivation scales fine (sub-ms at 100+ passes). The genuine scale walls are all backend-side and none is architectural: the DX12 descriptor ring hard-fails at ~85 textured draws/frame (L-32), every textured draw allocates a fresh descriptor set on Vulkan (L-32), DX12 rebuilds its pipeline key with string concat + SHA-256 over DXIL *per draw* (L-31), uploads block on queue-idle per resource (L-34), and there is no submesh-range/indirect draw verb (L-35) and no compressed-texture pipeline (T-10). Each has a clear fix; together they are the "make it a game engine, not a demo engine" backlog.

**Advanced-graphics headroom.** The maintainer's core worry — does the architecture foreclose adopting advanced techniques later — has a clear answer: **nothing is foreclosed.** Every surveyed technique (bindless, GPU-driven, mesh shaders, ray tracing, async compute, VRS, temporal upscalers, multi-view/XR) extends the existing vocabulary rather than fighting it. Two cross-cutting pinch points account for most of the future seam work: **(A)** the counts-only positional descriptor-binding contract and **(B)** the whole-resource single-subresource barrier/state model (both detailed under L-42). Both are additive to fix, and (A) is half-fixed already — the WebGPU backend parses the per-binding reflection data the desktop backends throw away. The WebGPU backend has **not** dumbed down the neutral layer (verified in reverse — L-42).

**What to build next.** Input (L-05 epic) and audio (L-06 epic) proposals are fully designed below, including library choices and API sketches. `Loom.Concepts` has a prioritized 10-item expansion list plus an explicit rejection list (L-45/L-46). The tooling section (T-01…T-14) is dominated by one observation: the engine's *data* surfaces for tooling are already excellent (graph/plan dumps, timings, inspection edges, deterministic capture) — most proposals are "put a real front end on a seam that already exists."

## Strengths (verified, not assumed)

- **The seam is genuinely clean.** No graphics-API type or package reaches `Loom.Core`/`Loom.Graph`; all mapping switches fail loud; `Queue.AsyncCompute` throws at derive; plans are advisory and the WebGPU backend *proves* it by ignoring `BarrierPlan`/`AliasPlan` entirely and consuming only `AttachmentAction`s. Three backends with radically different sync models run off one neutral plan.
- **Derive-once is real.** `SetGraph` derives `GraphSchedule → BarrierPlan → AliasPlan/LifetimePlan` exactly once; per-frame work is plan iteration over `ImmutableArray`s. Resize does not re-derive.
- **The hot path is remarkably allocation-clean** for a codebase this young: `DrawCall` is a `ref struct`; Vulkan/WebGPU pipeline lookups use `[InlineArray]`-backed value keys; uploads ride retire-based rings; descriptor writes are `stackalloc`; delegates are preallocated. Only three leaks were found (all trivial to fix).
- **Hazard derivation is correct and well-reasoned** — WAR edges target readers, `.Blends` modeled as read+write, same-layout write hazards still barrier, aliasing birth-barriers widened correctly; the comments prove the reasoning.
- **`EngineBase` is a real backend-common layer** — the WebGPU backend inherited lifecycle, shadows, readback, timing, and hot-reload unchanged.
- **The MSBuild/SDK engineering is unusually careful** (incremental-shared-module trap, FastUpToDateCheck trap, culture-code trap — each handled with an explanatory comment). One project → desktop exe or wasm app purely by RID.
- **Where fail-loud is implemented, messages are excellent** — derive errors name the pass and resource and suggest the fix.
- **Debug markers/object names are mature on both backends** (nested RenderDoc/PIX trees from dotted pass names), and the graph + all four derived plans are dumpable.
- **Docs exist and are mostly good** (`getting-started`, `effect-cookbook`, `api-vocabulary`, `llms*.txt` for agent consumption) — drift issues are listed below, but the habit is rare at this stage.

# Part A — Hosting & application lifecycle

### L-01 · Give `LoomApplication` access to input — a hosted game is display-only today
**Category** hosting/input · **Severity** Critical · **Effort** M (host half of the L-05 epic)

**Where:** `Loom.Hosting.Desktop\DesktopAppHost.cs:27-74` (creates the Silk window locally, hooks only `FramebufferResize`+`Render`, never calls `window.CreateInput()`, never exposes the window); `Loom.Hosting.Web\WebAppHost.cs:114-115` (no pointer/keyboard handler — the hand-rolled browser gallery wires one at `Loom.Web\Program.cs:117` but it never graduated); `Loom.Core\Hosting\LoomApplication.cs:40-56` (the full app surface is `Configure`/`LoadContent`/`Update`/`Draw` — no input hook); `Loom.Hosting.Desktop\Loom.Hosting.Desktop.csproj:27-30` (references `Silk.NET.Windowing` only; `Silk.NET.Input` is referenced solely by the sandbox).

**What & why:** A game created from `templates\loom-app` cannot read a single key press — not even "press Escape to quit". The only input-capable host in the repo is `Loom.Sandbox\Program.cs`, which does **not** use `DesktopAppHost`: it hand-rolls the window, input context, a 70-line Silk-`Key`→`VirtualKey` mapping table (`Program.cs:797-865`), modifier gathering, and UI queueing. The "reusable host" and the only working input plumbing are disjoint, so every game would copy ~300 lines of `Program.cs`.

**Recommendation:** The desktop host owns a Silk.NET input context and pumps it into the neutral queue defined by L-05; the web host owns a DOM-events JS shim doing the same (the pattern `loom-webgpu.js` already established). See L-05 for the full design.

### L-02 · Complete the `LoomApplication` lifecycle: exit, surface size, settings, backend choice, suspend, unload
**Category** hosting · **Severity** High · **Effort** S–M

**Where:** `Loom.Core\Hosting\LoomApplication.cs`, `AppOptions.cs`, `Loom.Hosting.Desktop\DesktopAppHost.cs:48-52`, `Loom.Core\Hosting\IEngine.cs`.

**What & why:** Holes a real game hits in week one:
1. **No exit.** The window is local to `DesktopAppHost.Run`; there is no `Exit()`. "Quit from the pause menu" is unimplementable.
2. **No surface size / aspect.** `FramebufferResize` is wired straight to `engine.Resize` and never surfaced; `IEngine` has no size getter. A hosted app **cannot compute a projection aspect ratio** — `Camera.Perspective(fovY, aspect, …)` is unusable under the reusable host (both samples dodge this by drawing fullscreen triangles).
3. **No `EngineSettings`.** `DesktopAppHost.cs:48-49` hardcodes `new EngineSettings { PreferredBackend = backend.Name }` — no `VSync`, `HdrOutput`, `MaxFramesPerSecond`, `WatchShaderDirectory`; and `EnableValidation` defaults `true`, so every packaged game requests validation layers.
4. **No backend choice.** `ResolveBackend()` takes `AvailableEngines[0]`.
5. **No unload hook.** No `UnloadContent`/`OnClosing` counterpart to dispose app resources before the engine (the sandbox calls `engine.WaitIdle()` manually, `Program.cs:574`).
6. **No suspend/focus events.** Minimize forwards `FramebufferResize(0,0)` → `engine.Resize(0,0)` unguarded; no `Suspended/Resumed`/focus-change (audio ducking, pause-on-focus-loss, and input reset all need it).

**Recommendation (issue-ready):**
```csharp
public abstract class LoomApplication {
    protected void Exit();                          // host closes window / stops rAF loop
    public Vector2 SurfaceSize { get; }             // updated by the host before each Tick
    protected virtual void OnResize(int w, int h);  // after engine.Resize
    protected virtual void OnFocusChanged(bool focused);
    protected virtual void UnloadContent();         // before engine disposal
}
```
`Configure(AppOptions)` gains an `EngineSettings` (or `AppOptions` embeds one) and a backend selector. Host duties: skip `engine.Resize`/`Tick` while 0×0, call `UnloadContent` + `WaitIdle` on close. All additive; nothing names a game concept.

### L-03 · Graduate the sandbox's host machinery into `Loom.Hosting.Desktop`
**Category** hosting · **Severity** Medium-High · **Effort** M

**Where:** `Loom.Sandbox\Program.cs:605-672` (window creation branching on backend + settings), `LaunchOptions.cs` (whole option surface) vs `Loom.Hosting.Desktop\DesktopAppHost.cs:54-70` (a hand-rolled 15-line `--capture` that admits "Not the full launch-option surface") and `:103-109` (private re-implementation of arg parsing). `docs\getting-started.md:69-121` teaches a *third* copy (fully manual bring-up).

**What & why:** Three divergent hosts exist, and the two capture protocols already disagree (host grabs frame 3; sandbox grabs frame 60 after exposure convergence; web gallery frame 60, `WebAppHost` frame 10) — so a game published on the reusable host cannot be verified with the same golden/parity pipeline the engine itself uses. Every real game wants exactly these flags (windowed size, vsync, capture-for-bug-reports, smoke for CI).

**Recommendation:** Promote a `HostOptions` parser (the `LaunchOptions` grammar) into `Loom.Hosting.Desktop`: `--backend`, `--vsync/--no-vsync`, `--max-fps`, `--hdr`, `--capture <path>` (adopting the sandbox's frozen-time frame-60 protocol so game captures are pixel-comparable), `--smoke-frames N`, `--watch-shaders`; app args flow through untouched. Then shrink `Loom.Sandbox\Program.cs` to consume it — the sandbox becomes the reference `LoomApplication` instead of a parallel universe. Fix the `EngineSettings.MaxFramesPerSecond` duality while there (`EngineSettings.cs:26-30` — with a real host, the host owns it).

### L-04 · Add the fixed-timestep hook now
**Category** hosting · **Severity** Medium · **Effort** S

**Where:** `Loom.Core\Hosting\FrameTime.cs:7-10` explicitly defers it; both hosts tick variable-rate only.

**What & why:** Physics, deterministic simulation, and replays need accumulate-and-step; left unprovided, every game rebuilds the accumulator and gets the spiral-of-death clamp and interpolation alpha subtly wrong.

**Recommendation:** Host-side accumulator, Core defines only the hook: `AppOptions.FixedStepHz` (0 = disabled); host calls `FixedUpdate(FixedTime step)` 0..N times (clamped, e.g. max 5) before `Update`; `FrameTime` gains `float Alpha` (render interpolation fraction). Identical logic in both hosts keeps desktop/browser simulation-compatible.

### L-05 · **Epic: build `Loom.Input`** — action maps, rebinding, gamepad, touch, UI arbitration
**Category** input · **Severity** High (the largest "around the engine" gap) · **Effort** L overall (M core + desktop adapter; M gamepad/touch/web/rebinding persistence)

**Current state (evidence):** Input source is Silk.NET.Input, sandbox-only (`window.CreateInput()` at `Loom.Sandbox\Program.cs:252`; first keyboard/mouse only, lines 253-254). No gamepad/joystick anywhere in the repo (grep: zero matches). Touch types exist in SUIsei but "only mouse is currently driven" (`external\SUIsei\SUIsei\Input\PointerInput.cs:12`). Routing is ad-hoc fan-out: raw Silk events forwarded to *all* consumers unconditionally — SUIsei `QueuePointer` **and** the demo's `OnPointer` (`Program.cs:296-298`); keyboard has a hard-coded Tab carve-out (`Program.cs:257-275`); ImGui polls separately (`Program.cs:451-457`). `FlyCamera` polls `IKeyboard`/`IMouse` directly (`Loom.Sandbox\FlyCamera.cs:44-77`) — the only reason it's stranded in the sandbox instead of Concepts. `FrameInputs` deliberately carries no input and should stay that way.

**Decision — where it lives:** a **new `Loom.Input` project**. Not Concepts (Concepts is app/scene meaning over neutral channels; input is a platform-device subsystem with host adapters, persistent state, serialization — it deserves its own package). Not the hosting packages (the types must be shared by desktop host, web host, headless tests, and game code; hosting packages are RID-conditional). Layering: `Loom.Input` is dependency-free (no Silk, no Loom.Core) → each host owns a thin adapter (desktop: `Silk.NET.Input` pump incl. `IGamepad` + `ConnectionChanged` hotplug; web: DOM `pointer*`/`keydown`/Gamepad-API JS shim). SUIsei keeps its own input types (standalone submodule); the glue converts — the existing `ToVirtualKey` table written once in the adapter instead of per game.

**Design:**
- *Events + snapshot, both neutral.* Adapters enqueue `InputEvent`s (device kind, code, value, pointer id, timestamp) into a preallocated ring; once per frame the host drains it through a router and folds into an `InputSnapshot` backed by preallocated buffers (keyboard bitset, mouse state, `GamepadState[4]`, `TouchPoint` span). No steady-state allocation; no reflection; **source-generated** `System.Text.Json` context for binding persistence — NativeAOT-clean.
- *Action maps built once, like a graph* — declarative, hashable, typed handles so per-frame lookup is an array index:
```csharp
var actions = InputActions.Define(b =>
{
    b.Button("jump",  Key.Space, Pad.South);
    b.Vector("move",  Composite.Wasd, Pad.LeftStick, deadzone: Deadzone.Radial(0.2f));
    b.Axis  ("zoom",  Mouse.Wheel, Pad.Triggers);
    b.Button("pause", Key.Escape, Pad.Start).IgnoreUICapture();
});
actions.Rebind("jump", Pad.East);                        // runtime rebinding = serializable overlay
File.WriteAllText(path, actions.SaveBindings());         // JSON via source-gen
actions.LoadBindings(json);
```
```csharp
protected override void Update(FrameTime time)
{
    var input = Input.Snapshot;                     // host-built, allocation-free view
    if (input.Pressed(jump)) …                      // edge
    var move = input.Value(moveVec);                // deadzoned Vector2
    if (!input.UIWantsPointer) camera.Look(input.PointerDelta);
    Engine.Write(viewProj, camera.ViewProjection);  // input → neutral Constants, as today
}
```
- *Pillar fit:* input reaches the game **only** as per-frame data in `Update`; anything a shader needs rides `Constants`/`Storage` exactly as camera data does now. The graph never sees input; closures stay pure; `FrameInputs` untouched.
- *Gamepad:* multiple pads (index-addressed + `Connected`), hotplug as connection edges in the snapshot, radial/axial deadzones + response curves as binding processors, rumble as a small command queue the adapter drains (Silk exposes `IGamepad.VibrationMotors` — cheap to include in v1).
- *Touch:* raw `TouchPoint`s (id, phase, position, timestamp) in v1; **defer gesture recognition** to a later Concepts helper (SUIsei owns UI-side gestures; game gestures are design-specific).
- *UI-vs-game arbitration:* the router runs sinks in order (SUIsei → ImGui → game); the snapshot carries `UIWantsPointer`/`UIWantsKeyboard`; bindings opt out per action (`IgnoreUICapture` for pause/push-to-talk). **Requires the SUIsei-side `UIHost.WantsPointer`/`WantsKeyboard` flags — filed as S-14 in the SUIsei review.**

**Decision points:** (a) snapshot delivery — `protected InputSnapshot Input` property (non-breaking, recommended) vs widening `Update(FrameTime, InputSnapshot)`; (b) rumble in v1 (recommended: yes); (c) migrate `Loom.Sandbox` onto it immediately (recommended: yes — deletes ~150 lines and makes the sandbox the reference consumer).

### L-06 · **Epic: create `Loom.Audio` on miniaudio**
**Category** audio · **Severity** High (nothing exists; every game needs it) · **Effort** L (M core mixer/buses/one-shots/streaming; M 3D + web shim)

**Current state:** verified absent — grep for `audio|sound|OpenAL|miniaudio|FAudio` across all `.cs`/`.csproj`/`.props`/`.md`/`.slnx`: zero matches.

**Home & posture:** a new **`Loom.Audio`** project with **zero dependency on Core/Graph** — audio shares nothing with rendering except the frame loop; keeping it dependency-free preserves "Loom is a rendering engine" while shipping the subsystem games expect beside it. Constructed in `LoadContent`, `audio.Update()` called in `Update`; only hosting touchpoint is L-02's `OnFocusChanged` (pause/duck on focus loss).

**Native layer — recommendation: miniaudio.**

| Candidate | License | AOT/interop | What you get | Concerns |
|---|---|---|---|---|
| **miniaudio** | MIT-0/public-domain | single C file, `[LibraryImport]` P/Invoke — AOT-clean | device backends (WASAPI/CoreAudio/ALSA/Pulse), high-level `ma_engine`: mixing, groups (buses), fades, 3D spatialization, wav/flac/mp3 (+stb_vorbis) decoders | you build/ship per-RID natives yourself (matches the repo's "offline precompiled artifacts" posture); browser needs a JS shim |
| Silk.NET.OpenAL | binding MIT; **OpenAL Soft is LGPL** | Silk already in-stack | 3D sources natively | no decoding/streaming/buses — you write the mixer anyway; LGPL friction for static/console futures |
| FAudio (FNA) | zlib | C ABI | XAudio2-shaped, battle-proven | drags SDL; submix-voice-shaped, lower-level than needed |
| SDL3 audio | zlib | C ABI | device + streams | no 3D, minimal mixing |

miniaudio is the only one covering device + mixer + groups + 3D + decoding in one MIT-0 blob; it is the de-facto standard C audio layer (raylib, many shipped games).

**Scope v1:** device init + format negotiation with graceful no-device (null device, API still works); **buses** `master → { music, sfx, ui, voice }` with per-bus volume/pitch and **ducking** as side-chain rules (voice active → attenuate music by N dB, attack/release); **one-shots** from a preallocated voice pool (steady-state allocation-free); **streaming music** (miniaudio data sources, double-buffered); **3D spatialization** — the *game* hands `Loom.Audio` positions from its own camera (the two subsystems never reference each other); **threading**: the native callback thread is miniaudio's; the public API is a lock-free command ring + parameter snapshots drained by frame-synced `audio.Update()` — no locks, no GC interaction on the callback thread; generation-checked `VoiceHandle` so a finished one-shot can't be use-after-freed.

```csharp
using var audio = AudioSystem.Create(new AudioSettings { SampleRate = 48_000 });
var sfx   = audio.CreateBus("sfx",   audio.Master);
var music = audio.CreateBus("music", audio.Master);
audio.AddDuck(trigger: voiceBus, target: music, attenuationDb: -9, attack: 0.05f, release: 0.4f);

var clip   = audio.LoadClip(File.ReadAllBytes("hit.wav"));   // resident, decoded
var stream = audio.OpenStream("music/overworld.ogg");        // streamed
audio.Play(clip, sfx, volume: 0.8f, pitch: RandomPitch());   // pooled one-shot
var h = audio.Play3D(clip, sfx, position);                   // VoiceHandle
audio.SetListener(camPos, camForward, camUp, camVelocity);
h.Position = emitterPos;  h.Stop(fadeOutSeconds: 0.2f);
audio.Update();                                              // once per frame
```

**Browser:** miniaudio doesn't run under browser-wasm; define `IAudioDevice` as the seam now, ship a WebAudio JS shim later (the `loom-webgpu.js` pattern). Don't block v1 on it.

**Decision points:** (a) miniaudio vs OpenAL (the LGPL question and the missing mixer are the deciders); (b) audio decode lives in `Loom.Audio` via miniaudio, not `Loom.Assets` (recommended — keeps Assets render-focused); (c) HRTF/attenuation knobs in v1 or defaults-only (recommended: defaults-only).

### L-07 · Resolve the `FrameInputs.DrawLists` dead channel (two UI-submission mechanisms, one unused)
**Category** hosting/API hygiene · **Severity** Medium (docs/pillar contradiction) · **Effort** S–M

**Where:** No host populates it — all three `engine.Render(new FrameInputs {...})` call sites set only `DeltaSeconds`/`Time` (`LoomApplication.cs:78`, `Loom.Sandbox\Program.cs:551-555`, `Loom.Web\Program.cs:366`). Meanwhile `UIPainter.Draw` reads `_host.DrawLists` from the **captured** `UIHost` (`Loom.UI.SUISei\UIPainter.cs:76`) — the exact pattern the pure-closure pillar forbids — and all backends dutifully plumb `inputs.DrawLists` through (`Loom.Backend.Vulkan\VulkanEngine.cs:331`, `DirectX12RenderContext.cs:108`, `WebGpuEngine.FrameRecord.cs:31`).

**What & why:** The painter-captures-the-host pattern won in practice, leaving `FrameInputs.DrawLists`/`IRenderContext.DrawLists` as documented-but-unused plumbing across four assemblies. New backends will keep implementing it; new UI integrations won't know which channel is canonical; docs and sandbox contradict each other.

**Recommendation:** Pick one. (a) Make `LoomApplication.Tick` forward a registered `UIHost`'s lists through `FrameInputs` (also gives the hosted lifecycle its missing UI slot — pairs with L-01/L-02); or (b) bless "stable painter objects may be captured; per-frame *data* may not" in the pillar text and delete `FrameInputs.DrawLists` + backend plumbing. (a) is the principled fix; (b) is the cheap one.

### L-08 · Support headless / surface-less engine creation
**Category** hosting/scale · **Severity** Medium · **Effort** M–L per backend

**Where:** `Loom.Core\Hosting\IRenderBackend.cs:22` — `Create(object surface, …)` requires a live window surface; the sandbox's "headless" modes still create a real window (`Program.cs:54`); golden/parity tests are therefore GPU-gated and CI-skipped.

**What & why:** CI screenshot regression without a desktop session, dedicated-server builds, and off-screen tooling (asset bakers) are all blocked on the mandatory surface.

**Recommendation:** `backend.Create(Surface.Offscreen(w, h), settings)` where present becomes a no-op/readback target (`g.Present` renders into a readable image; `RequestCapture` already extracts pixels). Vulkan needs no surface at all (skip swapchain); DX12 similarly (no HWND). Unlocks CI software rasterizers (T-06). Phase 2: a null backend for server builds (an `IRenderBackend` that accepts everything, does nothing).

# Part B — Authoring API & ergonomics

### L-10 · Fix the `DrawCall.SetUniforms(in T)` dangling-span footgun — the README models the broken pattern
**Category** footgun · **Severity** High · **Effort** M

**Where:** `Loom.Core\Hosting\DrawCall.cs:82-83`, `README.md:63`.

**What & why:** `SetUniforms<T>(in T value)` stores `MemoryMarshal.CreateReadOnlySpan(in Unsafe.AsRef(in value), 1)` — a span aliasing the caller's storage, escaping ref-safety. The doc warns "bind it to a local, not a temporary" — but the README's canonical example is `call.SetUniforms(obj.ModelMatrix)`. If `ModelMatrix` is a *property* (the common case), the compiler materialises a hidden temp that dies at the end of the statement; by `ctx.Draw(call)` the span points at a dead stack slot. It "works" in most builds, then corrupts per-draw data under JIT stack-slot reuse — the worst bug class, zero diagnostics. The sandbox's own `DemoDraw.Mesh` carefully uses an explicit local, showing the required discipline.

**Recommendation:** Make `SetUniforms` **copy** into per-call scratch (stage eagerly into the existing per-frame uniform ring, or a fixed inline buffer on `DrawCall` for blocks ≤ 256 B) — deletes the footgun class for a few bytes of copy. At minimum fix the README example.

### L-11 · Stop leaking the shader toolchain into compute-technique authoring
**Category** footgun · **Severity** High · **Effort** M

**Where:** `Loom.Core\Materials\TechniqueDescriptor.cs`; `Loom.Sandbox\Demos\SkinningDemo.cs:44-48`, `ParticlesDemo.cs:27`; `build\Loom.Sdk\Loom.Shaders.targets:85-94`.

**What & why:** A compute technique today is `new TechniqueDescriptor("skin", VertexEntry: "main", FragmentEntry: "main", IsCompute: true, …)` — the compute entry rides `FragmentEntry`, and must be `"main"` because slangc renames a lone compute entry in SPIR-V while the DXIL emit uses `-entry computeMain`. The correct value of a Core-layer field depends on a slangc quirk that differs per backend artifact. Worse, the DXIL emit hardcodes `-entry vertexMain/fragmentMain/computeMain` and detects stages by **raw text search** (`ReadAllText(...).Contains("vertexMain")`) — so the `VertexEntry`/`FragmentEntry` customisation the descriptor advertises works only on Vulkan; on DX12 a custom-named entry is silently never compiled and fails at runtime.

**Recommendation:** (a) Add `ComputeEntry` (or a `TechniqueDescriptor.Compute(shader, entry)` factory); (b) backends resolve the SPIR-V rename internally (try declared name, fall back to `"main"` for sole-entry modules) so authors always write `computeMain`; (c) make the SDK honour declared entry names (item metadata on the `.slang` item) or error explicitly on non-canonical names; match on `[shader("...")]` attributes instead of `Contains()`.

### L-12 · Add record-time validation — undeclared resources currently bind anyway
**Category** footgun · **Severity** High · **Effort** M

**Where:** `Loom.Backend.Vulkan\VulkanRenderContext.Verbs.cs` (whole file), `VulkanRenderContext.cs:227-242, 271-274`, `Loom.Backend.DirectX12\DirectX12RenderContext.Binding.cs:82`.

**What & why:** The derive layer honours fail-loud; the record layer largely doesn't. Traced misuse outcomes:

| Misuse | Today |
|---|---|
| Read-before-write in graph; unwritten present target | ✅ `GraphValidationException`, great message |
| `engine.Write` to undeclared/mis-sized handle | ✅ clear exception |
| `ctx.FullScreen("blit", hdr)` where the pass **forgot `.Samples(hdr)`** | ❌ no check — binds in whatever layout; garbage or validation spam in dev, silent corruption in Release |
| `ctx.Draw` with a `Mesh` but technique declared without `HasVertexInput` | ❌ no check — undefined |
| `DrawCall` with `Mesh = null`, no GPU instances | ❌ `call.Mesh!.Value` → bare "Nullable object must have a value" |
| Typo'd technique name | throws at first frame; **different exception type + message per backend** (see L-13) |
| Push floats when reflected uniform slots are full (Vulkan) | ❌ **silently dropped** (`VulkanRenderContext.cs:227-242`); DX12 throws for its analogue — an error-handling parity break |
| Push > 16 floats | ❌ silently truncated on both backends |

**Recommendation:** The record context knows the active pass's declared access list — add a validation mode (on when `EngineSettings.EnableValidation`, compiled out otherwise) checking at `FullScreen`/`Draw`/`Dispatch` time: every bound handle declared with matching access on the current pass; `Mesh`-vs-`HasVertexInput` agreement; `Mesh == null` requires `VertexCount > 0` + GPU instances, with messages naming pass + technique. Make push overflow/drop an error, not a truncation.

# Part C — Execute-layer correctness

### L-27 · Derive readback keep-alive in `BarrierPlan` — write-only readback targets can read back garbage
**Category** correctness · **Severity** Medium (latent; silent; backend-divergent) · **Effort** S–M

**Where:** `Loom.Graph\BarrierPlan.cs:101-103` (store derivation ignores `ReadbackTargets`); `Loom.Backend.Vulkan\VulkanEngine.Readback.cs:19-22` (hard-codes pre-copy transition as `ShaderReadOnlyOptimal → TransferSrcOptimal`); contrast `Loom.Graph\LifetimePlan.cs:56-60` (which handles it correctly for aliasing).

**What & why:** If a readback target's last graph use is the pass that *writes* it (nothing samples it afterwards), its attachment derives `StoreAction.DontCare` — on a tile-based GPU (including the maintainer's Adreno X1-85, which honors DONT_CARE) contents are discarded before `RecordReadback` copies them. The Vulkan pre-copy transition additionally assumes the last use was a `.Samples`. DX12 tracks real state and is robust — so the backends silently diverge. Current demos happen to sample their pick buffers last; a game will eventually hit the other shape, and it fails silent.

**Recommendation:** In `BarrierPlan.Derive`, treat every `ReadbackTargets` id as used-after-everything (force `Store`) and emit a derived end-of-frame transition so backends stop assuming the from-state. Add a `BarrierPlanTests` case: readback target whose last use is a write → `Store`.

**Category** correctness · **Severity** Medium · **Effort** M

# Part D — Backend performance & scale

### L-31 · Give the DX12 context a value-typed pipeline-key front cache
**Category** perf · **Severity** High · **Effort** S

**Where:** `Loom.Backend.DirectX12\DirectX12TechniqueCache.cs:31-89`, called per draw from `DirectX12RenderContext.Verbs.cs:16,111,190`, `DirectX12RenderContext.cs:160`.

**What & why:** Every `Draw`/`FullScreen`/`Dispatch` on DX12 rebuilds the cache key with string concatenation (`key += "|" + (int)format`) **and computes SHA-256 over the full vertex+pixel DXIL bytecode** — per draw, every frame. Both a hot-path allocation violation and real CPU cost scaling with draw count. Vulkan and WebGPU both front their content-hash caches with an allocation-free `PipelineKey` dictionary (`VulkanRenderContext.cs:76-80,271-299`); DX12 is the odd one out.

**Recommendation:** Mirror Vulkan's `PipelineKey` (technique string + `[InlineArray]` formats + depth flags); fall through to the content key only on miss (keep the digest for hot-reload correctness).

### L-32 · Fix the DX12 per-frame descriptor budget; cache material descriptors on both backends
**Category** perf-scale · **Severity** High (hard scale wall on DX12) · **Effort** M (short term) / L (bindless endgame)

**Where:** `Loom.Backend.DirectX12\DirectX12Engine.cs:113` (`DescriptorRing(512, 2)` → **256 descriptors/frame**, overflow throws), `DirectX12RenderContext.Binding.cs:17,97` (`CreateShaderResourceView` per texture per draw); `Loom.Backend.Vulkan\VulkanRenderContext.Binding.cs:16,93` (fresh `Allocate` + `UpdateDescriptorSets` per draw), `VulkanRenderContext.DrawListLayers.cs:130-142` (**one descriptor set per UI `DrawCommand`**, even for the same texture).

**What & why:** A scene with a few hundred textured draws hard-fails on DX12 (~85 three-texture material draws) while Vulkan keeps going — a scale wall *and* a backend behavioral divergence. On Vulkan, 10,000 draws = 10,000 set allocations/updates per frame; a 200-command UI = 200 sets/frame. The allocator's own doc calls a cached/bindless scheme "a later optimisation".

**Recommendation:** Short term: (a) grow the DX12 ring on demand (heap chain, mirroring `VulkanDescriptorAllocator`) or size from the graph + a draw budget; (b) cache persistent SRV tables / descriptor sets per (material, layout) — materials are immutable and `MaterialStore` gives a stable id; (c) frame-local memoisation in the draw-list path (reuse the last set when the texture is unchanged — collapses the UI case). ### L-47 · UI-bridge performance batch: cache resolved textures, skip unchanged draw lists, size group-opacity layers to their rect
**Category** perf-hot-path (UI glue + backends) · **Severity** Medium-High · **Effort** S / M / M

**Where:** `Loom.UI.SUISei\UIPainter.cs:110-137` (`ResolveTextures`), `UIPainter.cs:74-105` (no `Revision`/`Damage` reads); `Loom.Backend.Vulkan\VulkanRenderContext.DrawListLayers.cs:73-110` + `VulkanLayerTargets.cs` (same shape on DX12/WebGPU).

**What & why:** Three Loom-side halves of the SUIsei rendering path (SUIsei-side halves are in the companion review):
1. **`ResolveTextures` allocates every frame** whenever the UI references any image: `new Texture[max + 1]` per `Draw` call — a per-frame-always pillar violation for any UI with an `Image`. Worse, `max` derives from `ImageSource.TextureIndex`, a *global* monotonic counter (`ImageSource.cs:13,18`), so the array grows with every `ImageSource` ever created, and `_imageTextures` never evicts. Cache keyed by `draw.Revision`; grow a persistent array like `ImGuiPainter`'s scratch; consider eviction + per-list texture indices.
2. **`Revision`/`Damage` are produced but never consumed on the GPU path.** Every frame re-uploads the full vertex/index/command streams through the per-slot bump ring and re-records all draws even when the compositor's no-op path returned the identical list. This is the engine-side half of the per-render-target caching direction ("cached = persistent + skippable producers"): a persistent (not ring) vertex/index buffer per UI surface uploaded only on `Revision` change, plus (later) graph-level pass skip when every producer is clean. `SUIsei.Gallery`'s software host already proves the consumption pattern.
3. **Group-opacity layers render full-surface.** Each `BeginLayer`/`EndLayer` costs two render-pass breaks + a clear on a **full-surface** target regardless of the group's actual bounds, plus a full-surface composite quad — on the tile-based Adreno dev box, render-pass breaks with full-surface load/store are the most expensive thing a UI can do. The `BeginLayer` command already carries the layer rect as `ClipRect`; size the pooled layer image + render area to it. (Note: this changes the composite quad's UV mapping that the CPU oracle mirrors 1:1 — update `SUIsei.Rasterizer` in lockstep; see the companion review's open questions.)

# Part E — Advanced-graphics headroom

### L-42 · Headroom assessment: nothing is foreclosed; two pinch points to design once
**Category** headroom (assessment + two enabler issues) · **Severity** — · **Effort** per item

| Technique | Verdict | Primary pinch point |
|---|---|---|
| Timestamp queries / GPU profiling | **done** (Vulkan + DX12) | WebGPU leg absent (optional there) |
| HDR / wide-gamut output | **done / additive** | scRGB shipped; HDR10 metadata additive |
| Spatial upscalers (FSR1/CAS) | **additive today** | already expressible (`RelativeScale` domains + fullscreen pass) |
| Parallel command recording | **additive (backend-internal)** | single shared mutable `IRenderContext` (see below) |
| Async compute / multi-queue | **needs seam work (planned)** | single-timeline `BarrierPlan`; 1 queue/backend |
| Indirect / GPU culling / MDI | **needs seam work (planned, gap ①)** | CPU-int counts; no `IndirectArgument` state (L-35) |
| Bindless / descriptor indexing | **needs seam work** | pinch point A |
| Variable rate shading | **needs seam work (small)** | no shading-rate attachment role; needs capability gating |
| Temporal upscalers (FSR2/DLSS/XeSS) | **needs seam work** | gap ③ + no vendor-SDK pass escape hatch |
| Mesh shaders | **needs seam work** | VS/FS/CS-shaped `TechniqueDescriptor`; fixed SDK entry names |
| Hardware ray tracing | **needs seam work (largest)** | no AS resource kind; pinch point A first |
| Multi-view / XR | **needs seam work (largest)** | pinch point B; single-surface `Create` |

**Pinch point A — the counts-only positional binding contract** (its own issue): `ShaderReflection` stores only *counts* (`Loom.Graph\ShaderReflection.cs:19-25`); backends build layouts as "N samplers then M storage images…" at sequential bindings with `DescriptorCount = 1` (`VulkanTechnique.cs:84-107`), and authors must hand-number `[[vk::binding]]` in category order (a silent-miscompile trap). This is the wall in front of bindless, RT, and shader ergonomics — and the codebase already half-contains the fix: the slangc JSON carries per-parameter `binding.index`, and **the WebGPU backend already parses it** (`WebGpuBindingModel.cs:201`) while shared `ShaderReflection.FromBytes` throws it away. Extend `ShaderReflection` to `(index, kind, arraySize)` records (keep count properties as derived views); build Vulkan set layouts and DX12 root signatures from actual indices. Removes hand-numbering; gives bindless a landing zone (arrayed/unbounded entry → second set / SM6.6 heap indexing). **Effort M. Severity rises to High if the GPU-driven direction (Planning §7 decision 1) is taken.**

**Pinch point B — whole-resource single-subresource state model** (design note now, work when gap ② lands): `BarrierPlan` tracks one `ResourceState` per resource id (`BarrierPlan.cs:58`); Vulkan hardcodes `ImageSubresourceRange(aspect, 0, 1, 0, 1)` (`VulkanEngine.Barriers.cs:52`) and `LayerCount = 1` (`FrameRecord.cs:272`); `ResourceHandle`/`Domain` carry no mip/layer axis. This is Planning gap ② — but it also gates Hi-Z (per-mip states), single-pass CSM arrays, froxel volumetrics, **and multi-view/XR** (layered rendering + `ViewMask`). Design the transition granularity once — `(resource, mipRange, layerRange)` timelines with whole-resource as the fast path — with all four consumers in mind.

**Also:**
- **`EngineCapabilities` before the first optional GPU feature lands** (S): device features are all-or-nothing (`VulkanContext.cs:368-391`); GPU timing already grew a bespoke probe (`CanEnableGpuTiming`). Add an immutable caps record populated at engine creation, consumed by `SetGraph` validation ("graph uses mesh shading; engine lacks it → throw") — fail-loud made queryable. Fold `CanEnableGpuTiming` in.
- **Vendor-SDK / backend-implemented passes** (design note): DLSS/XeSS (and any native effect) need to record externally-owned GPU work inside a derived pass; `IRenderContext` deliberately exposes no native handle. A "backend-implemented pass" (declared with normal reads/writes so barriers derive; bodied by the backend; absent on backends without the SDK) would also give ImGui-class integrations a cleaner seam.
- **Async compute** is the best-prepared row: `Queue` exists, `ScheduledPass.DependsOn` preserves the true DAG, failure is loud. Missing: schedule partitioning, cross-queue semaphore derivation, per-queue timelines in `BarrierPlan`, queue-family ownership transfer, a second queue per backend. Pure engine work; no API break.
- **Parallel recording**: the plan is per-pass self-contained; blockers are backend-internal only (one primary command buffer, shared mutable context, slot-keyed rings, non-thread-safe descriptor allocation). Document the single-thread contract (currently comments-only; consider a debug thread-affinity assert in `EngineBase.Write`/`Render`) so backend refactors don't accidentally make it harder.

- **Asset database/content browser** — assets are app-owned files; build-time *baking* (T-05/T-10) is per-file and MSBuild-shaped instead.
- **A custom frame debugger** — backends already speak RenderDoc/PIX natively; integrate (T-04), don't compete.

## Open questions for the maintainer

1. **Is `LoomApplication` the real production path or a demo shim?** L-01/L-02/L-03's scope is only worth it if "real path." If serious games hand-roll hosts instead, the hand-rolled host needs to become the documented recipe and the template should say so. (Recommended: real path — the SDK/RID story is too good to waste.)
2. **Is the GPU-driven direction (Planning §7 decision 1) being taken?** Decides whether pinch point A (L-42) is next-quarter work or deferrable. L-35's indirect verb is worth doing regardless.
3. **Should subresource-granular barriers (pinch point B / gap ②) be designed for multi-view/XR at the same time?** Same `(mip, layer)` axes; designing once avoids reopening `BarrierPlan` twice.
4. **Input arbitration granularity:** coarse `WantsPointer`/`WantsKeyboard` (ImGui-style, S effort in SUIsei) or per-event consumption? Coarse covers the 95% case.
5. **`Update` signature vs `Input` property** for snapshot delivery on `LoomApplication`.
6. **Audio native layer:** accept miniaudio (MIT-0, self-shipped RID natives, matches the precompiled-artifacts posture) over Silk.NET.OpenAL (LGPL native, no mixer)? WebAudio shim in v1 or deferred?
7. **Which capture protocol becomes canonical** when the host machinery graduates (frozen-time frame-60 with exposure convergence, presumably) — decides whether existing goldens stay valid for host-based games.
8. **Multi-window:** one `IEngine` binds one surface for life while SUIsei's `UIHost` is already per-window. In scope (needs a device/engine split) or document "one engine per window"?
9. **Is `SetGraph`-with-equal-graph meant to be cheap** (L-22)? Docs say cached-by-hash; code always rebuilds.
10. **What is the intended resize semantic for `Persistent` contents** (L-28) — preserve or reset? They can't both be right at pixel parity.
11. **Is "second `.Writes` = LoadAction.Load" intentional API semantics?** It's tested, so deliberate — but it blurs `.Writes` vs `.Blends`; worth an explicit design note in Planning §3.
12. **Exception policy:** are backend-typed authoring exceptions acceptable, or is a neutral family (L-13) a hard rule like "no API types in Core"?
13. **Descriptor budget philosophy** (L-32): fail loud at a fixed budget (DX12 today) or grow silently (Vulkan today)? Pick one posture.
14. **Is WebGPU expected to track feature parity or remain a demo-subset backend?** Shapes how aggressive `EngineCapabilities` (L-42) needs to be.
15. **Tooling distribution boundary** (T-12): verification tooling in `Loom.Sdk`, the `loom` tool, or repo scripts?
16. **WARP/lavapipe fidelity** (T-06): measure whether software rasterization holds the 4/255 parity bar before scoping the CI lane.
